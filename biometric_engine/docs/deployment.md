# Deployment: CI/CD and Render (Fase 10)

## Pipeline overview

| Workflow | Trigger | What it does |
| -------- | ------- | ------------ |
| `biometric-engine CI` (`.github/workflows/ci.yml`) | push to `main`, any `pull_request` | `lint` (ruff + mypy), `test` (pytest, coverage gate `--cov-fail-under=90`), `build` (`docker build`) |
| `biometric-engine deploy` (`.github/workflows/deploy.yml`) | `biometric-engine CI` completes on `main` with success | POSTs the Render deploy hook; **skips gracefully** when `RENDER_DEPLOY_HOOK` is unset |

The leftover `.github/workflows/jekyll-gh-pages.yml` is unrelated (stale
scaffold); leave it untouched.

## Secrets

| Name | Where it is used | Who provides the value |
| ---- | ---------------- | ---------------------- |
| `RENDER_DEPLOY_HOOK` | `deploy.yml` (deploy hook URL) | Render Dashboard > service `biometric-engine` > Settings > Deploy Hook (user copies it) |
| `JWT_SECRET_KEY` | Render web service env | Generated by the Blueprint (`generateValue: true`); never stored in GitHub |
| `DATABASE_URL` | Render web service env | Wired by the Blueprint (`fromDatabase: biometric-postgres`); never stored in GitHub |
| `REDIS_URL` | Render web service env | Wired by the Blueprint (`fromService: biometric-redis`); never stored in GitHub |

Only the deploy hook needs a GitHub secret, because the Blueprint wires the
three runtime variables Render-side. Set it (run this yourself; values are
user-dependent and are never committed):

```bash
gh secret set RENDER_DEPLOY_HOOK --body "https://api.render.com/deploy/srv-XXXX?key=YYYY"
gh secret list
```

## Render Blueprint onboarding

1. Render Dashboard > New > Blueprint > select this repo (`render.yaml` at root).
2. Confirm the three resources: web service `biometric-engine` (Docker),
   database `biometric-postgres` (PostgreSQL 15), Key Value `biometric-redis`.
3. Apply. Render generates `JWT_SECRET_KEY` and injects `DATABASE_URL` /
   `REDIS_URL` into the web service.
4. Copy the service Deploy Hook (Settings) into the GitHub secret above.
5. Merge to `main`: CI runs, then `deploy.yml` fires the hook.

`autoDeployTrigger` is `off` in the Blueprint on purpose: releases go
through the CI-gated hook, so a push alone never ships untested code.

Render injects `DATABASE_URL` as a plain `postgresql://` connectionString,
but the app creates an async (asyncpg) engine. `normalize_database_url`
in `app/infrastructure/db/session.py` rewrites the driver-less form to
`postgresql+asyncpg://` at engine creation (URLs that already name a
driver pass through untouched) — do not hand-edit the dashboard value to
add the driver.

## Local CI parity run

Same commands the workflows run, against the local backing services
(postgres `localhost:55432`, redis `localhost:56379`, DB `biometric_test`):

```bash
cd biometric_engine
python -m ruff check app/ tests/
python -m mypy app/
DATABASE_URL=postgresql+asyncpg://biometric:biometric@localhost:55432/biometric \
REDIS_URL=redis://localhost:56379/0 \
JWT_SECRET_KEY="$(grep '^JWT_SECRET_KEY=' .env | cut -d= -f2-)" \
  python -m pytest tests/ -q --cov=app --cov-report=term-missing --cov-fail-under=90
docker build -f biometric_engine/docker/Dockerfile biometric_engine  # from repo root
```

Env vars on the command line override `.env` (pydantic Settings precedence:
process env > `.env` file), which is exactly how the CI job injects
`DATABASE_URL` / `REDIS_URL` / `JWT_SECRET_KEY`.
